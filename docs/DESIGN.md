# 设计取舍

## 1. 它解决的真实问题

8051 实验需在编译器、Proteus 和人工判波形间切换；没有插件，模型只能给代码。本插件提供五个工具，并区分截图观察与确定性验证（`lib/index.js:1-20,100-214`）。

## 2. 架构与接线方式

`lib/index.js:~35-214` 的 `apply(ctx)` 注册五个工具；每个先检查 `exec.signal` 再转成 kernel CLI 子命令。内核负责编译、仿真和离线 verify，插件只做宿主适配。测试守护清单、README 和路径卫生（`test.mjs:196-240`）。

## 3. 为什么这么设计（取舍）

放弃把编译与 Proteus 逻辑塞进入口：内核可独立测试和替换后端。放弃截图判定：`mcu_verify` 返回 running/evidence 结构化证据（`lib/index.js:155-195`）。放弃单一编译器：自动优先 Keil、可回退 SDCC（`lib/index.js:138-152`）。

## 4. 不变量与坑

五个工具名必须与实现、清单和 README 一致；执行前必须 `throwIfAborted()`；源码路径要求纯 ASCII；不得写入盘符绝对路径（`lib/index.js:129-210`、`test.mjs:206-240`）。`mcu_sim` 不等于验证。

## 5. 扩展点

新工具从 `ctx.tools.register(defineTool(...))` 开始；新后端进入 kernel 并补离线测试；模板能力扩展内核索引，不把机器文件打包。


实现时应优先沿用现有宿主接口，而不是复制宿主内部实现。这样做的收益是升级时差异面小、测试能直接覆盖边界；代价是插件必须尊重宿主的生命周期、序列化和取消语义。遇到文档与代码不一致时，以当前入口实现和仓库测试为准，并把未确认的兼容性记录在变更说明中。
